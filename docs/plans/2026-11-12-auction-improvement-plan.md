## 1. 요약: 결론이 어떻게 바뀌었나

v1의 방향(통계 집계 → 구간 예측 → ML)은 맞습니다. 하지만 **그 전에 데이터 파이프라인 자체가 네 군데에서 고장 나 있어서**, 지금 상태로 통계를 집계하면 잘못된 숫자를 학습하게 됩니다. 순서를 "응급 복구 → 대시보드 → 데이터 보강 → 통계 → 엔진"으로 바꿉니다.

**가장 급한 것 (v1에 없던 내용)**

1. ~~매일 수집(010)이 매일 실패 중~~ → **정정:** n8n이 성공한 실행은 저장하지 않도록 설정돼 있어 기록이 실패 건만 남아 있었음. 11-05~11-09에 30분 타임아웃 실패가 있었던 것은 사실이나, 현재는 수집이 성공 중(사용자 확인).
2. **양산 물건은 울산지방법원 사건인데 "창원지방법원"으로 저장됨.** 373건 전부 법원이 창원으로 되어 있고, 양산 114건 중 99건의 매각물건명세서 첫 줄이 "울산지방법원"입니다. 012가 창원법원으로 결과를 조회하니 양산 물건 결과는 거의 잡히지 않습니다.
3. **"변경"(기일변경) 결과를 처리하지 않아 물건이 영원히 멈춤.** 매각기일이 지났는데 아직 "진행중"인 물건이 **125건**(8월분 11건 포함). 012는 이들을 매일 밤 다시 크롤링하느라 25~45분씩 걸립니다.
4. **유찰 횟수가 매일 밤 1씩 부풀어 오름.** 다음 기일이 안 잡힌 유찰 물건은 매일 "유찰"로 다시 판정돼 `loss_count + 1`. 최대값 39회(실제로는 약 5회), 373건 중 **119건**이 최저가/감정가 비율과 2회 이상 어긋납니다. 엔진(유찰 횟수별 표)과 대시보드 "유찰 횟수별 낙찰가율" 차트가 모두 이 값을 씁니다.
5. **유찰 뒤 목표가가 다시 계산되지 않음.** 012는 최저가만 내리고 `bid_target`은 그대로 둡니다. 예: 2025타경12507은 1회 유찰 뒤 낙찰됐는데 목표가가 감정가 그대로(1억3,400만)라 "오차 +36.6%"로 기록됐습니다. 엔진이 틀린 게 아니라 **채점이 틀린 것**입니다.

**v1에서 맞았던 것 (확인됨)**

- 복합통계 테이블(`m8dnx8345q8ryww`)은 비어 있음. 16번 조회 모두 0건, 진행중 373건 전부 `bid_confidence = 낮음` → 엔진은 100% 하드코딩 표(82/76/70/65/60%)로 계산 중.
- 대시보드: 인수금액·보증금 필드 미요청, ROI에 인수금액 미반영, 프로필 복원 버그, API 무인증, XSS, 양도세 단순화.

**v1에서 틀렸거나 고칠 것**

- "엔진이 인수금액을 무시" → **아님.** 엔진은 기준가에서 `inherited_amount`를 이미 뺍니다. 빠진 곳은 **대시보드 ROI**입니다.
- "매각기일을 `2026.11.05` 문자열로 저장" → **아님.** NocoDB 날짜 컬럼이 `2026-11-11`로 정규화해 저장합니다.
- "실거래가 미수집(사이트 개편 후 0자)" → 원인은 사이트 개편이 아니라 **크롤러 3초 타임아웃**(실거래 AJAX 응답이 최대 6.2초). 같은 응답에 **전월세 실거래도 들어 있어**, 국토부 API 키 없이 먼저 고칠 수 있습니다.
- "표본 확대(6단계)는 크롤러에 수집을 새로 붙여야" → 012의 `/track`이 이미 법원·기일 단위로 결과를 긁고 있으므로, 그 응답 범위를 넓히는 작은 수정으로 가능합니다.
- `/api/item`이 "인증 없음" 목록에 있었지만 더 큰 문제는 **GET 링크로 상태가 바뀐다**는 점입니다(아래 3-2).

### 3단계 · 통계 집계 + 통계 탭

- n8n 새 워크플로우(012 직후 매일): 결과 테이블에서 지분·일괄·이상치를 빼고 단계별(단지 → 읍면동 → 시군구×용도 → 법원×용도) × 유찰회차별로 낙찰가율 중앙값·사분위수·표본 수·평균 응찰자 수를 계산해 통계 테이블에 저장. 감정가 기준과 시세 기준을 따로 저장.
- 010 `복합통계조회`를 단지명 완전일치에서 **계층 조회**로 변경(단지 → 동 → 시군구 순으로 표본 충분한 단계 사용).
- 대시보드 통계 탭: 회차×지역×용도 박스플롯(5건 미만 흐리게), 월별 낙찰가율·응찰자 추이, 시세 대비 낙찰가율 분포, **엔진 성적표**(목표가로 썼다면 이겼을 비율, 평균 절대오차, 치우침, 월별). 성적표는 0-5 이후 데이터만 사용.

### 4단계 · 엔진 V4

1. **기준 분리**: 시세 있으면 "낙찰가/시세" 분포, 없으면 "낙찰가/감정가" 분포. 섞지 않음.
2. **계층형 축소 추정**: 단지 표본이 적으면 상위 단계 값 쪽으로 당김.
3. **확률 출력**: 비슷한 물건의 낙찰가 분포 + 유찰 기록(그 가격엔 아무도 안 씀)으로 "이 금액이면 낙찰 확률 약 30/50/70%"인 P30·P50·P70 금액 제시. 각 금액의 세후 ROI를 같이 표시.
4. **최저가보다 낮게 나오면 "이번 회차 비추천 · 다음 회차 예상 최저가 ○○"**로 표시(최저가로 끌어올리지 않음).
5. **GAP SCORE 재설계**: 예상 낙찰가(P50)와 시세의 차이 + 권리 위험 + 데이터 신뢰도. 목표가를 시세와 다시 비교하는 순환 제거.
6. **백테스트 후 교체**: 2단계에서 쌓인 결과로 V3 대비 오차·승률을 비교해 이긴 경우에만 교체.

### 5단계 · 시세·매도가

- 크롤러 실거래 수집 수정(REPORT.md 방법): `pageview.php mode=1`을 Referer 붙여 직접 호출, 타임아웃 10초 이상. **매매(#mainDiv1) + 전월세(#mainDiv2)** 모두 저장.
- 그래도 부족한 물건은 국토부 실거래가 API(공공데이터포털 무료 키)로 보완.
- 비교 거래 보정(같은 단지·면적 ±10%, 층·시점 보정, 중앙값, P25~P75, 거래 건수 표시). 빌라는 같은 동·연식·면적의 ㎡당 가격.
- ROI의 전세가를 "매도가 × 65%" 대신 전월세 실거래로.
- 24개월 뒤 매도가 비관/기본/낙관(연 -3/0/+3%) 세 가지 ROI.

### 6단계 · ML (나중)

결과 이벤트(지분 제외) 300건 이상일 때 NAS 파이썬 컨테이너에서 LightGBM 분위수 회귀 주 1회 학습, 예측값만 NocoDB에 기록. 2단계 표본 확대로 도달 시점이 크게 당겨질 것으로 예상.
